Q24

Single-parse vs trend handling

Blueprint §6.4.5 spec: "Add 'Aging trend' — if historical parses exist (v1.1), show whether 0–30 bucket is growing or shrinking. v1 placeholder: tooltip 'Trend available after second parse.'" Question is how the v1 product handles the surface where a trend module would eventually sit. Three panels: tooltip (per blueprint), inline label (more visible), or hide entirely (cascade to v1.1 feature spec).

Appears on: Insights → Collections · same Q23.A surface · trend treatment differs across A/B/C

Same Q23.A aging-bar surface across A/B/C. Decision is on where the v1.1-trend feature lives in v1.

ATooltip placeholder · per blueprint
Aging buckets · trend
tooltip-on-hover · "Trend available after second parse"
Trend available after second parse
Hover the chart → tooltip appears: "Trend available after second parse." No persistent visual weight; the missing feature is invisible until the user goes looking. Cost: users may not discover the tooltip — affordance is implicit. Benefit: first-paint chart is clean; the v1 surface looks complete, not under-construction.
BInline label · below chart
Aging buckets · trend
inline label below chart · always visible
Aging trend available after second parse
Persistent inline label below the chart, with info-icon prefix. Affordance is explicit — the user knows a v1.1 feature is coming. Cost: always-on visual weight on a missing feature. The v1 surface advertises its own incompleteness on every load. Reads as "under construction" rather than "complete v1."
CHide trend module · cascade to v1.1
Aging buckets
no trend module in v1 · ships in v1.1 once second-parse exists
No trend module rendered in v1. The aging chart ships standalone; the trend feature lands in v1.1 once a second parse exists for the deal. Benefit: v1 surface ships complete — no placeholder, no hover-to-find, no advertised incompleteness. Cascade: v1.1-feature policy needs an entry: "trend module spec'd in §6.4.5, lands when historical-parse data path exists." No code stubs in v1.
Claude's recommendation C. Hide the trend module entirely in v1. Two reasons: (1) placeholder UX is asymmetric — every user who triggers the tooltip (A) or sees the inline label (B) gets a negative impression ("this product is missing a feature") with zero corresponding positive impression for users who don't go looking; (2) v1 should ship complete — Basis is positioned as IC-memo grade. Advertising what's missing on every load is the opposite of institutional confidence. C cascades cleanly: once a second parse exists for the deal, the trend module lands as a v1.1 enhancement, and the only required artifact is a v1.1-feature-policy entry pointing at §6.4.5.

Honest read on A: A is the blueprint's stated v1 placeholder, so picking C means amending the blueprint. The amendment is small (delete the tooltip line in §6.4.5, add "Trend module ships in v1.1") but it's a real edit. If the blueprint's intent is to signal forthcoming features to users, A wins; if the intent is to ship complete v1 surfaces, C wins. My read is the latter — placeholders communicate "draft" to institutional readers.
